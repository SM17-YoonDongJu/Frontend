# 프론트 통합 QA 방법론

핵심: "파일이 존재하는가"가 아니라 **"인접 레이어의 shape이 일치하는가"**. 통합 버그는 단일 파일이 아니라 레이어 경계에서 난다. 각 모듈 완성 직후 점진적으로 검증한다(전체 완성 후 1회 몰아치기 X).

## 경계면 교차검증 (핵심)
두 레이어를 **동시에 열어** shape을 비교한다. 한쪽만 보면 못 잡는다.

| 경계 | 비교 방법 | 흔한 버그 |
|------|----------|----------|
| MSW 핸들러 ↔ zod 스키마 | 핸들러 응답 객체를 `schema.parse`에 넣어보기 | 필드명 오타, 누락 필드, enum 값 불일치 |
| zod `z.infer` ↔ 쿼리 훅 반환 | 훅 반환 타입이 스키마 타입과 같은가 | `parse` 누락→`any`, 배열/단건 혼동 |
| 훅 반환 ↔ 컴포넌트 소비 | 컴포넌트가 접근하는 필드가 타입에 있는가 | 없는 필드 접근, optional 미처리(`?.`), undefined 인덱스 |
| 쿼리키 ↔ 무효화 호출 | 뮤테이션 invalidate 키 == 쿼리 등록 키 | factory `_def` 범위 불일치 → 캐시 안 지워짐 |
| staleTime 정책 ↔ 화면 요구 | 폴링 화면이 staleTime 0 + refetchInterval 인가 | 리스트가 stale 안 됨 → 갱신 누락 |

**검증 절차:** 경계마다 양쪽 파일을 읽고 → shape 표로 정리 → 불일치를 버그로 기록. 추측 금지, 실제 코드 인용.

## 실행 검증 (증명)
추측하지 말고 실제 실행:
```
pnpm typecheck     # tsc --noEmit — 경계 타입 불일치 다수 여기서 잡힘
pnpm lint          # eslint — prefer-const, eqeqeq, no-console
```
- 실패 시 **에러 전문 인용** + 원인 레이어 지목. "통과했을 것"이라 쓰지 않는다.
- `noUncheckedIndexedAccess` 위반(배열 인덱스 undefined 미처리)은 흔하니 우선 확인.

## 행동 기반 테스트 (Playwright + MSW)
구현 세부가 아닌 **사용자 행동**으로 테스트(규칙: 구현보다 행동 기준).

> **환경:** Playwright 설치 완료(`@playwright/test`), 실행은 `pnpm --filter @insurance/web test:e2e`. 스펙은 `apps/web/e2e/*.spec.ts`에 이미 여러 개 있다. **이 repo에서 스펙을 실제로 어떻게 쓰는지(파일 구조·셀렉터·하이드레이션 가드·MSW 사용·헬퍼)는 `references/e2e-authoring.md`를 읽고 따른다.** 새 스펙은 기존 패턴에 맞춘다.
```ts
// 나쁨: expect(component.state.count).toBe(0)   ← 구현 결합
// 좋음: 사용자 관점
test("리포트 없으면 빈 상태 노출", async ({ page }) => {
  // MSW가 빈 배열 반환하도록 핸들러 override
  await page.goto("/내리포트");
  await expect(page.getByText("받은 리포트가 없어요")).toBeVisible();
});
test("분석신청 제출하면 결과로 이동", async ({ page }) => {
  await page.goto("/분석신청");
  // 사고유형 선택 → 입력 → 제출 → 결과 화면 검증
});
```
- 3상태(빈/에러/정상): happy-path는 기본 핸들러로, **고가치 빈/에러·롤백은 E2E에서 핸들러 override로** 검증, 저가치는 정적 레이어(zod·TS)에 위임(`references/e2e-authoring.md` 참조).
- 실행을 못 했으면 추측으로 통과 보고하지 말고 **시나리오를 문서로 명세 + "실행 보류 사유" 기록**(거짓 통과 금지).

## 테스트 전략: E2E-only + 강한 정적 레이어 (이 프로젝트 확정)

이 프로젝트는 **단위·통합테스트를 하지 않는다.** Vitest/RTL/Jest 도입 안 함. 런타임 테스트는 **Playwright E2E가 유일**하다. 대신 아래 **정적 레이어가 하위 테스트를 대체**한다 — "테스트 안 하는 빈자리"가 아니라 의식적 대체다:

| 보통의 하위 레이어 | 이 프로젝트의 대체 |
|---|---|
| 단위테스트(타입·shape) | **TS strict + zod 런타임 검증** — 필드 누락·타입 불일치·shape 위반은 여기서 잡힘 |
| 통합테스트(계약) | **api-spec 린트 훅 + MSW 계약 거울 + 경계 교차검증(아래)** |
| 사전 게이트 | **pre-commit typecheck·lint** |

따라서 "엣지는 통합테스트로 내린다" 같은 말은 쓰지 않는다(내려갈 레이어가 없다). 대신 **E2E로 올릴지 / 정적 레이어에 맡기고 의식적으로 안 할지**를 명시적으로 가른다.

### 무엇을 E2E로 올리나 (꼭 테스트할 핵심 흐름)
> **핵심 흐름 정의 — 아래 중 하나라도 해당하면 E2E로 테스트한다:**
> 1. **사용자가 이 서비스를 쓰는 주된 목적 그 자체** — 고객 분석신청 제출·리포트 생성, 사정사 검수→발행, 매칭, 로그인/회원가입.
> 2. **한 번 잘못되면 되돌리기 어렵거나 데이터가 잘못 저장되는 동작** — 제출, 상태 변경(예: 검수 전송), 결제.
> 3. **여러 화면·단계가 이어져 중간에 끊기기 쉬운 흐름** — 단계 폼(분석신청 6단계 같은 퍼널).
> 4. **권한이 틀리면 안 되는 길목** — 로그인 안 한 사람 차단, 남의 리포트 접근 차단, 고객/파트너 화면 분리.
>
> 판단 한 줄: **이게 조용히 망가진 채 배포되면, 사용자가 핵심 작업을 아예 못 하게 되나? → 그러면 테스트한다.**

**E2E에 올릴 것:**
1. 위 핵심 흐름의 정상 동작(성공 케이스) 전체.
2. **타입·zod가 못 잡는, 가치 높은 예외** — 진입 가드(앞 단계 안 하고 뒷단계 직접 진입), 역할별 라우팅(`/customer/*`↔`/partner/*`), 세션, WebView↔네이티브 브릿지, **사용자가 실제 보는 에러/빈 화면**.
3. 배포마다 손으로 반복 확인하던 회귀 지점.

**E2E에 올리지 말 것 (→ 테스트하지 않고 정적 레이어에 맡김):**
- 필드 형식·범위 검증 → zod가 런타임에 강제(테스트 불필요).
- 타입·shape 불일치 → TS·api-spec 훅이 잡음.
- 단일 컴포넌트 로컬 상호작용(토글·동적 추가 등) — 저가치면 **의식적 미테스트**로 두고 백로그가 아니라 "안 함"으로 기록(갈 곳 없는 "RTL로 내림" 금지).
- 저가치 엣지를 E2E에 욱여넣지 마라 — E2E가 유일한 런타임망이라 비대해지면 느려지고 깨져서 *전부* 신뢰를 잃는다.

### 에러·빈 상태도 E2E가 떠안는다 (하위 레이어가 없으므로)
happy-path만으론 부족하다. **사용자에게 보이고 가치 있는** 빈/에러/롤백 상태는 **E2E에서 MSW 핸들러 override로 직접 검증**한다(`references/e2e-authoring.md`). 단 고가치만 — 모든 에러 경우를 넣지 않는다.

### 작성 원칙 (좋은 테스트의 속성)
유일한 런타임망이라 **결정적·격리·행동 기준**이 특히 중요하다.
- **북극성**: 테스트가 실제 사용 방식을 닮을수록 신뢰가 커진다 — 구현(state·함수)이 아니라 사용자가 보는 결과를 검증.
- **결정적**: 같은 코드면 항상 같은 결과. 조건분기·랜덤·고정 sleep 금지. 첫 상호작용/내비 유실은 `expect(async()=>{ click; assert }).toPass()`로 재시도.
- **격리**: 테스트마다 fresh navigation, 자체 상태(쿠키·스토리지). 순서·공유 의존 금지.
- **빠름·구체적 실패**: web-first 단언(`toBeVisible`). 실패가 "무엇이 왜"를 짚게.
- **사용자 중심 셀렉터**: `getByRole`/`getByText`/`getByLabel`/placeholder. CSS 클래스·XPath·`data-*` 남발 금지.
- **happy-path 우선** 후 고가치 엣지. 퍼센트 논쟁(70/20/10 등) 신경 X — 의미 있는 이유로 실패하는 표현력 있는 테스트가 본질.
- 플레이키한 테스트는 즉시 고치거나 격리. 신뢰 잃은 스위트는 아무도 안 본다.

> 실제 작성 패턴(파일 구조·셀렉터·`toPass` 가드·핸들러 override·헬퍼)은 `references/e2e-authoring.md`.

새 화면이면 CUJ happy-path 1~2개 + 고가치 가드/에러를 E2E로. 저가치 엣지는 "정적 레이어에 위임(미테스트)"로 명시.

## 코드 컨벤션 리뷰
`code-conventions` 스킬 4원칙으로 리뷰. 동작이 맞아도 위반은 보고하되 분류:
- **blocker**: 동작 버그, 타입 에러, 경계 불일치, 데이터 유실
- **nit**: 컨벤션 위반(매직넘버, 네이밍, 과결합) — 권고

## 점진 검증 타이밍
- data-engineer 완료 직후 → 데이터 경계(MSW↔zod↔훅)부터
- ui-builder 완료 직후 → UI 경계(훅↔컴포넌트) + 3상태 존재
- 통합 후 → 행동 테스트 + 회귀(이전 QA에서 고친 버그 재발 여부)

## 리포트 형식
`_workspace/04_qa_<feature>.md`에 경계 검증표 + 실행 결과(인용) + 컨벤션 위반 + 테스트 결과 + blocker/nit 분류. 버그는 책임 에이전트(data-engineer/ui-builder)에게 직접 전달.
