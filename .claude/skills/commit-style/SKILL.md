# 커밋 메시지 컨벤션

실제 커밋 24개 분석 + 팀 결정(2026-06-18)으로 확정. **직접 커밋하지 말 것 — 메시지만 추천**하고 사용자가 직접 커밋한다.

## 형식

```
<type> : <한글 명사형 요약>

* <변경 1 — 명사형>
* <변경 2 — 명사형>
```

- **콜론 양옆 공백**: `feat : ...` (✅) / `feat: ...` `feat:...` (❌)
- **type 전부 소문자**: `feat` `design` `refactor` (✅) / `Design` `Refactor` `[Design]` (❌)
- 제목 끝에 마침표 없음.

## type 어휘 (전부 소문자)

| type | 용도 |
|------|------|
| `feat` | 기능·화면·컴포넌트 추가/구현 |
| `fix` | 버그 수정 |
| `design` | 레이아웃·헤더·푸터·디자인 토큰 등 UI 셸 (동작 없는 시각 구현) |
| `refactor` | 동작 불변 구조 개선 |
| `docs` | 문서·스토리북 스토리 |
| `test` | 테스트 추가/수정 (Playwright E2E) |
| `chore` | 라이브러리 설치·설정·빌드 |
| `style` | 포맷·세미콜론 등 비기능 |
| `settings` | 프로젝트/모노레포 초기 세팅·하네스 |

판단 모호하면 "이 커밋의 핵심 변화가 무엇인가"로. 시각 셸만이면 `design`, 동작 추가면 `feat`.

## 제목 (subject)

- **한글 명사형 종결**: "구현", "추가", "도입", "구성", "수정", "초기화" 등. ("구현했다"/"구현함" ❌, "구현" ✅)
- **스코프는 괄호로**: `feat : 손해사정 요청 퍼널 4단계(보험금 입력) 구현`
- 한 줄로 무엇을 했는지 명확히. 50자 내외 지향(한글이라 유동적).

## 어휘 (흔한 개발 용어로)

- **종결 동사**(명사형, 통용 개발 용어): 추가 · 구현 · 수정 · 제거 · 분리 · 통합 · 리팩터링 · 마이그레이션 · 적용 · 도입 · 정리 · 처리 · 연동 · 검증.
- **명사도 통용어로**: 훅 · 스키마 · 핸들러 · 컴포넌트 · 타입 · 모듈 · 유틸 · 엔드포인트.
- **지어낸/어색한 표현 금지** — 실제 커밋·개발 현장에서 안 쓰는 말 만들지 말 것. 예: "동반" ❌ → "같은 커밋에 포함" / "스토리 추가".
- **스토리북**: `* Storybook 스토리 추가` (✅) / "스토리 동반" ❌.

### 지양 → 지향 어휘 (실제 커밋 로그 기준)

문어체·번역투·직역 단어 금지. 왼쪽 쓰지 말고 오른쪽으로.

| 지양 (❌) | 지향 (✅) |
|----------|----------|
| 뮤테이션 (음차) | mutation 훅 (조회는 query 훅) |
| 무효화 | 갱신 |
| 골격 | 기본 구조 / 뼈대 |
| 데이터 경계 / Boundary | 에러 바운더리 |
| 도출 | 추론 / 생성 |
| 레이아웃 셸 | 레이아웃 |
| 계약 (contract) | 스키마·타입 정의 (단, `데이터 계약 정의`는 팀이 씀) |
| 연동 | 적용 / 추가 / 연결 |
| 조회 연동 | 조회 함수·훅 추가 |
| happy-path | 핵심 흐름 / 정상 흐름 |

### 자주 쓰는 어휘 팔레트 (로그에서 추출 — 이 안에서 골라 써라)

- **종결 동사:** 추가 · 구현 · 도입 · 구성 · 정의 · 적용 · 연결 · 전환 · 보강 · 재구성 · 보정 · 정리 · 제거 · 분리 · 추출 · 통합 · 지원 · 변경 · 수정
- **명사:** 훅 · 조회 훅 · 조회 함수 · 스키마 · 핸들러 · MSW 핸들러 · 컴포넌트 · 타입 · 쿼리키 · 캐시 상수 · 진입점 · 상태 화면 · 목 데이터 · 필터 · 레이아웃 · 검증 · 가드 · 폴백 · 페이지네이션

> react-query 훅: 조회는 `query 훅`/`조회 함수`, 변경은 `mutation 훅`. 한글 음차("뮤테이션") 금지.

## 본문 (body)

### 말투 — 한 명사구로 녹여 명사형 종결

각 불릿은 **"무엇을 했는지"를 하나의 명사구로** 쓴다. 행동과 대상을 `— `(엠대시)로 쪼개지 말고, 설명을 수식어로 앞에 녹여 명사형 동사로 끝낸다.

- ❌ `우측 sticky 초안 패널 컴포넌트 추가 — 선택 사건의 리포트 상세를 재사용해 표시`
- ✅ `선택 사건의 리포트 상세 정보를 재사용하는 우측 패널 추가`
- ❌ `필터 훅에 사고 유형·지역 상태 추가 — URL 쿼리(type·region) 동기화`
- ✅ `사고 유형·지역 필터 상태 및 URL 동기화 추가`

엠대시는 단발성 단일 불릿에서 짧게만 허용(`검수 시작 버튼 추가 — 검수 작성 화면으로 이동`). 다불릿 feat에선 쓰지 말 것.

**구현 디테일은 목적으로 풀어 써라.** 내부 방식(모듈 스코프·필드명 등)을 그대로 박지 말고 "왜 그렇게 했나"로. 영문 필드명도 한글 개념어로.
- ❌ `목 데이터 고정` / `보류 여부(held) 필드 추가`
- ✅ `보류 상태가 목록에 반영되도록 MSW 핸들러 추가` / `목록 응답에 보류 상태 필드 추가`

**훅·함수 불릿은 역할과 동작을 풀어라.** 이름만 박지 말고 "무엇을 하고, 성공/조건 시 무엇이 일어나는지".
- ❌ `보류 mutation 훅 추가`
- ✅ `사건 보류 요청을 보내고 성공 시 검수 대기 목록을 갱신하는 mutation 훅 추가`

### 불릿 문자

- **feat·fix·refactor·docs·test → `*` 불릿.** 변경 2개 이상 나열, 각 줄 명사형 종결.
  ```text
  feat : AI 초안 정보 패널 추가

  * 선택 사건의 리포트 상세 정보를 재사용하는 우측 패널 추가
  * 보상 가능 범위·AI 쟁점·분석 근거·추가 확인 항목 표시
  * 쟁점 상태별 배지 톤 적용
  * 미선택 및 로딩 상태 화면 추가
  * 목록·상세 2단 레이아웃으로 재구성
  ```
- **chore·settings·design(인프라/설정/의존성) → `-` 불릿 + 서술형 허용.** 무엇·왜를 한두 문장으로 풀어 써도 됨(아래 §라이브러리 참고).
- **단순/단일 변경 → 평문 1~2줄** 또는 본문 생략.
  ```
  feat : 퍼널 단계 진입 가드 추가

  직접 단계 진입 시 선행 단계 완료 여부 검증
  미완료 단계로 리다이렉트 처리
  ```
- "왜"가 제목/디프에서 안 보일 때만 본문에 사유 추가. 자명하면 생략.

## 라이브러리/의존성 추가 (chore)

라이브러리를 설치하는 커밋은 **`-` 불릿으로 각 패키지를 `이름@버전: 용도` 형식**으로 나열한다. 버전 명시 필수, 끝은 "용도".

```text
chore : zod, react-hook-form, @hookform/resolvers 라이브러리 추가

 - zod@4.4.3: 단계별 입력 스키마 정의·런타임 검증, API 응답 envelope 파싱 용도
 - react-hook-form@7.79.0: 퍼널 전체 폼 상태 관리·단계별 부분 검증 용도
 - @hookform/resolvers@5.4.0: react-hook-form ↔ zod 스키마 연결 용도
```
```text
chore : @playwright/test 설치 및 E2E 설정 추가

 - @playwright/test@1.61.0 : 프론트엔드 페이지 E2E 테스트 용도
 - MSW 모킹을 위해 chromium으로 dev 서버 띄워 테스트하도록 설정
 - test:e2e 스크립트 추가
```

세팅(`settings`)·인프라 도입도 같은 결: `-` 불릿로 도입 패키지·버전·목적을 풀어 쓴다(예: `react-query(v5.101.0) + devtools 추가, QueryProvider 전역 래핑`).

## AI 말투 검사 (메시지 확정 전 필수)

메시지 초안을 잡았으면 **확정·추천 직전에 `ai-tell-detector` 에이전트로 한 번 거른다.** 커밋 본문이 번역투·기계적 병렬·상투구로 "AI가 쓴 티"가 나는 걸 막는 게이트.

절차:
1. 위 규칙대로 메시지 초안(제목+본문)을 작성한다.
2. 초안 전문을 `ai-tell-detector` 에이전트에 넘긴다. 이때 **커밋 컨벤션상 정상인 것은 지적 대상에서 빼라고 명시**한다 — 명사형 종결(`~추가`/`~수정`), 가운뎃점(·) 나열, 영문 식별자(`tsconfig`·`api-spec` 등)는 정상이므로 제외. 실제 어색한 구간(장문 수식·압축 과다·번역투·불필요한 접속)만 짚게 한다.
3. 검출 결과 반영:
   - **S1/S2(강·중)** → 해당 불릿을 `suggested_fix` 방향으로 고친다(컨벤션 위배 없는 선에서).
   - **S3(약) 이하** → 가독성 손해가 분명할 때만 손보고, 아니면 그대로 둔다(커밋 메시지는 압축이 미덕).
   - **0건** → 그대로 확정.
4. 수정본이 다시 컨벤션(콜론 공백·소문자 type·명사형 종결·불릿 문자)에 맞는지 확인 후 확정.

> 짧은 단일 평문 커밋이거나 라이브러리 나열(`-` 불릿)처럼 산문 여지가 거의 없으면 이 단계는 생략 가능. `*` 불릿 다불릿 본문일 때만 실효가 있다.

## 커밋 단위 (원자성)

- **한 커밋 = 한 의미 단위.** 컴파일·검증 가능한 최소 단위로 쪼갠다.
- 데이터 레이어: fetch 함수 단독은 무의미 → 스키마 1커밋, (API+훅+목) 1커밋처럼 묶음.
- presentational 컴포넌트 + `.stories.tsx`는 소비처 없이도 1커밋 가능(스토리북 검증).
- "하나 구현 → 커밋 추천 → 다음" 흐름. 무관한 변경 섞지 않기.
- 공용 UI 컴포넌트는 `.stories.tsx`를 같은 커밋에 포함(스토리북 규칙).

## 추천-only 정책

- 작업 후 **커밋 메시지를 코드블록으로 추천만** 한다. `git commit` 직접 실행 금지.
- 변경 파일 목록 + 추천 메시지(제목+본문) 제시 → 사용자가 직접 커밋.

## 실제 이력 기준 예시 (정규형으로 교정)

```
feat : 손해사정 요청 퍼널 6단계(확인·제출) 구현

* 입력 정보 요약 화면 추가
* 필수 동의 검증 추가
* 분석 신청 제출 기능 추가
* 제출 성공·실패 처리 추가
* 분석 신청 훅 및 MSW 핸들러 추가
```
```
feat : report 쿼리키 factory·캐시 상수 도입
```
```
chore : zod, react-hook-form, @hookform/resolvers 라이브러리 추가
```
```
design : customer 고객 페이지 헤더 CustomerHeader 구현
```

## 관측된 드리프트 (이 규칙으로 수렴 대상)

기존 이력의 불일치 — 신규 커밋은 위 정규형만 사용:
- 콜론 공백 혼용(`feat:` vs `feat :`) → **`feat :`로 통일**
- type 대소문자 혼용(`Design`/`Refactor` vs `feat`) → **전부 소문자**
- 구버전 `[Design] ... (#14)` 대괄호+PR번호 squash 스타일 → 폐기
